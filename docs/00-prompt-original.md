# Codex 项目总指令：AI 海外达人营销助手（Influencer Marketing Copilot）

## 一、你的角色与项目目标

你是一名资深全栈工程师、AI 应用工程师和产品经理。请协助我从零开发一个可以实际运行、可以演示、可以接受面试追问的 AI 应用作品集项目。

我的开发环境与能力：
- 操作系统：Windows。
- 开发方式：Vibe Coding，主要通过与你对话来编写和修改代码。
- AI 模型：通过 DeepSeek API 调用大模型。
- 编程基础：初级，需要你提供清晰的开发步骤、运行命令、错误排查方法。
- 项目用途：秋招作品集，面向 AI 应用、产品运营、产品营销、海外营销、业务分析等岗位。
- 我的业务背景：有 TikTok 美区达人营销和海外市场营销相关经历，希望项目能体现真实业务理解，而不是简单包装成一个聊天机器人。

项目名称：AI 海外达人营销助手（Influencer Marketing Copilot）。

**核心目标：帮助海外营销人员从一批候选达人中，筛选出值得进一步人工评估的对象，解释匹配原因、展示证据与风险，并辅助完成优先联系名单的制定。**

本项目必须体现三个方面：
1. 业务问题拆解与产品设计能力。
2. 规则引擎、数据处理与 AI 语义分析相结合的能力。
3. 对 AI 局限、评估方法、数据质量和工程可靠性的理解。

不要为了展示技术而堆砌功能。请优先交付一个端到端可运行的 MVP，再决定是否需要扩展。

---

## 二、最高优先级：先解决核心问题，不要一开始做大而全

第一版只需要完整跑通以下用户旅程：

**配置营销任务 → 导入或加载达人数据 → 规则初筛 → AI 语义分析 → 查看推荐依据与风险 → 人工确认 → 导出结果。**

第一版不开发：
- 用户登录、权限系统、多租户。
- 数据库驱动的复杂 CRM。
- 多平台真实数据抓取。
- 自动联系达人、自动发送邮件或私信。
- 自动预测真实销售额、转化率或 ROI。
- 复杂的任务管理、审批流、团队协作。
- 付费部署、复杂云服务或不必要的微服务。
- 尚未证明有价值的智能体、多 Agent 协作、向量数据库等功能。

除非完成核心闭环并有明确证据表明某项功能确实必要，否则不要加入以上功能。

不要把“页面多、文件多、功能多”当成项目完成度。项目的成功标准是：用户能够完成一个真实合理的业务任务，并且能理解、核查和质疑系统给出的结果。

## 四、第一版产品设计

### 4.1 用户输入

用户通过简洁的表单创建一个营销任务，至少包含：

- 产品名称。
- 产品介绍或核心卖点。
- 目标市场，例如德国、西班牙、美国。
- 目标平台，例如 TikTok、Instagram。
- 目标受众。
- 营销目标，例如品牌曝光、内容种草、产品教育。
- 合作方式，例如产品置换、付费合作。
- 可选的预算范围。
- 可选的硬性要求，例如目标地区、最低粉丝量、内容语言。

字段不需要一次性全部填写。明确哪些字段是必填、哪些是可选，以及缺失时会产生什么影响。

不要将“品牌曝光”“产品种草”和“销售转化”当作同一种目标。不同目标应使用不同的评估侧重点。

### 4.2 达人数据

支持两种数据来源：

1. 加载项目内置的演示数据。
2. 上传用户自己的 CSV 文件。

演示数据至少包含 30 条达人记录，覆盖不同市场、平台、内容领域、粉丝量、互动表现和内容风格。数据应当具有业务上的差异性，而不是随机生成一堆相似记录。

建议字段包括：

- creator_id：唯一达人标识。
- creator_name：达人名称或明确标注为虚构的名称。
- platform：平台。
- market：主要市场。
- language：内容语言。
- follower_count：粉丝量。
- average_views：平均播放量。
- likes、comments：互动数据（如果可用）。
- engagement_rate：互动率（如果可用，必须注明计算口径或来源）。
- content_categories：内容领域。
- recent_content_summary：近期内容摘要。
- sample_content_text：代表性内容文本。
- audience_description：受众描述（如果有数据支持）。
- collaboration_history：合作经历（如果有）。
- data_source：数据来源。
- data_updated_at：数据更新时间。
- data_quality_notes：数据质量说明。

不要求每条记录都有全部字段。应当专门设计部分字段缺失的样例，检验系统是否能正确处理信息不足的情况。

数据规范：
- 演示数据必须明确标记为模拟数据。
- 不得把虚构达人、虚构播放量或虚构合作结果描述为真实业务数据。
- 不得编造真实平台账号、真实合作经历或未经验证的受众画像。
- 用户上传的数据必须保留可追溯的数据来源。
- CSV 解析失败时，给出具体原因与修复建议。
- 兼容常见 CSV 编码问题，并正确处理百分比、空值、数字格式和重复 ID。
- 不要悄悄丢弃无法识别的行或字段。

上传数据后，先展示预览、字段映射和校验结果。存在可修复的问题时，尽量让用户确认后继续，而不是直接报错退出。

### 4.3 规则初筛与评分

先使用确定性程序完成硬性条件过滤和基础指标计算，不要把简单数学计算交给大模型。

至少实现：

- 必要条件过滤。
- 缺失字段识别。
- 基础互动指标计算（前提是所需字段齐全且计算口径明确）。
- 候选达人基础排序。
- 每条达人记录的入选或排除原因。
- 规则配置和评分明细展示。

规则应当可配置、可解释，不能把未经验证的经验权重包装成行业标准。

例如，可以将内容相关性、目标市场匹配、受众匹配、互动表现和合作可行性作为候选评估维度，但必须区分：

- 硬性条件：不满足时可以排除。
- 软性指标：用于排序和人工参考。
- 信息不足：目前无法可靠判断。

不要将信息缺失自动视为 0 分或不合格。

每项评分都必须展示：
- 使用的字段。
- 计算或判断方法。
- 实际得到的结果。
- 数据缺失或口径不明时的限制。

如果没有可靠的行业基准，请将权重标注为“项目初始假设”或“可配置示例”，而不是宣称它们是行业标准。

### 4.4 DeepSeek AI 语义分析

只有通过基础硬性条件筛选后的候选达人，才进入 AI 语义分析。第一版默认只分析排名靠前的一小批候选人，例如 10 人；数量可以配置。

AI 负责：

- 分析产品卖点与达人内容的语义相关性。
- 判断达人近期内容是否适合当前营销目标。
- 分析内容风格与目标受众是否有合理的契合点。
- 从已提供的文本中识别潜在风险。
- 总结推荐理由与不推荐理由。
- 指出仍然缺少哪些关键信息。
- 给出需要人工核实的问题。

AI 不负责：
- 重新计算粉丝量、互动率等基础指标。
- 在没有证据时推断达人真实受众构成。
- 虚构达人历史合作、报价或过往转化数据。
- 声称可以保证销量、转化或 ROI。
- 把文本中的猜测写成事实。
- 在没有数据支持时给出精确的合作成功概率。

每条 AI 结论必须尽可能关联到具体的输入证据。例如，引用所提供的内容摘要或代表性文本，并解释为什么它与当前任务相关。

如果证据不足，应明确显示“信息不足，需人工核实”，而不是强行给出确定结论。

请设计结构化输出，至少包含：
- 内容相关性分析。
- 目标匹配分析。
- 推荐理由。
- 不匹配之处。
- 潜在风险。
- 证据及对应的数据字段。
- 缺失信息。
- 人工核查建议。
- 分析状态。

结构化输出必须经过校验。如果模型返回格式错误、缺字段、无效枚举或无法解析的 JSON，系统应有重试或明确失败提示，不得将错误内容直接展示为可靠结果。

如果模型给出了与原始数据矛盾的结论，应尽可能识别并标记冲突。

### 4.5 人工决策与导出

最终结果页至少展示：

- 达人基础信息。
- 规则筛选结果。
- 规则评分明细。
- AI 分析结论。
- 支持结论的证据。
- 潜在风险。
- 信息缺失提示。
- 推荐等级或人工优先级。
- 人工审核状态。

人工审核状态至少包括：
- 待审核。
- 建议联系。
- 暂不联系。
- 需要补充信息。

允许用户调整最终决定，并填写备注。AI 建议与人工决定必须分开保存和展示，不能因人工修改而覆盖原始 AI 结论。

支持将筛选结果和人工确认名单导出为 CSV，至少包含达人 ID、基础数据、规则结果、AI 结论摘要、风险、审核状态和人工备注。

导出内容必须注明使用的数据来源、分析时间及关键版本信息。不得在导出时悄悄删除失败分析或信息不足的记录。

## 五、关键工程要求

### 5.1 端到端优先

开发顺序必须是：

1. 建立最小可运行的应用。
2. 加载一小批模拟数据。
3. 完成规则初筛。
4. 接入 DeepSeek，分析少量候选人。
5. 在界面展示结果。
6. 完成人工审核。
7. 导出结果。
8. 验证整个流程后，再增加更多边界处理和评估功能。

不要先写完所有模块，再尝试拼接。

每次增加一个功能，都要检查它与前后环节是否兼容。

### 5.2 状态一致性与结果过期

每次分析都必须能够追溯到当时使用的：
- 达人数据版本或数据快照标识。
- 营销任务配置。
- 规则配置版本。
- AI 模型标识（以实际 API 响应或配置为准）。
- Prompt 版本。
- 分析时间。

如果用户更换数据、修改营销任务、调整规则或修改与分析有关的配置，旧分析必须被标记为“结果已过期”，不得继续当作最新结果展示或导出为最新分析。

用户可以重新运行分析，并查看哪些结果属于旧版本。

第一版可以使用轻量的本地状态或文件管理实现，不必为了版本管理引入复杂数据库。但版本信息必须真实记录，不能只在界面上显示一个没有实际含义的版本号。

### 5.3 DeepSeek API 的稳定性

- API Key 只能保存在本地环境变量或 `.env` 文件中。
- `.env` 必须加入 `.gitignore`。
- 提供 `.env.example`，但只能放占位符，不能包含真实密钥。
- 不得把 API Key 暴露在前端页面、日志、导出文件或提交到 Git 的代码中。
- 通过服务端调用 API。
- 设置合理的超时和错误处理。
- 对限流、网络中断、鉴权失败、模型返回格式异常分别提供可理解的提示。
- 不要因为 API 失败就伪造 AI 结果。
- 支持对单条失败记录重新分析，避免重复请求全部达人。
- 如果提供重试机制，应限制重试次数。
- 对请求做必要的缓存或去重，避免重复调用产生不必要的费用。
- 日志不得记录密钥或不必要的敏感数据。

如果 API 尚未配置，应用仍然应能通过演示数据完成规则初筛和界面演示，并清楚提示 AI 分析暂不可用。可以提供明确标记的预置演示结果，但不得将其冒充成刚刚由 API 实时生成的结果。

### 5.4 真实业务数据与演示数据隔离

必须区分以下内容：

1. 模拟达人数据。
2. 用户导入的业务数据。
3. 用于开发和测试的固定评估案例。
4. 实际运行产生的分析结果。

这四类数据不能混为一谈。

演示模式下的所有虚构结果必须有明显标识。真实数据模式不得自动混入虚构达人或模拟指标。

测试案例不能同时被当成模型表现的独立证明。如果案例被用于设计 Prompt 或调整规则，必须说明这一点，不能声称它仍是完全独立的测试集。

## 六、必须验证 AI 是否真的有价值

不能因为应用调用了大模型，就宣称它比传统筛选更智能或效果更好。

请建立一个小规模、可复现的离线评估机制，验证系统能否合理分析达人与营销任务之间的匹配关系。

### 6.1 固定评估集

在项目中建立固定评估案例，覆盖以下情况：

- 产品与达人内容高度相关。
- 产品与达人内容表面相关但目标不匹配。
- 达人内容相关，但目标市场不匹配。
- 数据不足，不能可靠判断。
- 存在可能影响合作的内容风险。
- 内容领域相关，但营销目标不一致。
- 基础指标表现较好，但语义匹配较差。
- 基础指标一般，但内容与目标高度相关。

每个案例应有人工编写的参考判断和判断依据，并明确说明案例为模拟测试案例，而非真实业务结果。

测试集规模以能够人工检查为准，第一版可从 12–20 个案例开始。不要为了追求数字而生成大量质量低下的案例。

### 6.2 比较方法

至少比较两种方案：

A. 仅使用规则引擎。

B. 使用相同的基础筛选结果，再加入 AI 语义分析。

在相同的任务和案例下，检查：
- 是否识别了内容与目标之间的匹配关系。
- 是否正确指出市场或受众不匹配。
- 是否在证据不足时选择保留判断。
- 是否出现无依据的事实陈述。
- 是否能给出与输入证据相对应的解释。

评估指标应当容易理解，并展示具体案例，而不是只给出一个总分。

可以记录人工参考标签与系统判断的一致情况，但不要把小样本结果夸大成统计上可靠的行业结论。

AI 方案未必在所有指标上优于规则方案。如果结果不理想，应如实呈现，并分析可能原因。

### 6.3 评估结果的可信度

- 固定评估案例与业务演示数据必须分开管理。
- 对参考答案、规则和 Prompt 的修改要有记录。
- 如果用评估结果调整 Prompt，需要说明该评估集已参与迭代，不再完全独立。
- 不允许自动生成一份宣称“AI 准确率达到 95%”之类、却没有实际运行记录的报告。
- 不得为了让 AI 显得更优秀而人为调整测试案例或隐藏失败案例。
- 评估报告必须记录执行时间、案例数量、失败数量、评估方法与限制。

第一版只需要证明评估方法是透明、可重复的，不需要追求漂亮的指标。

## 七、界面和演示要求

界面应像一个真正供海外营销人员使用的轻量业务工具，而不是默认样式的技术测试页面。

请优先保证：
- 任务创建入口清晰。
- 数据预览和校验结果易读。
- 筛选前后数量变化清楚。
- 规则与 AI 分析结果分开展示。
- 每项重要推荐都有依据。
- 信息不足和分析失败一眼可见。
- 人工审核操作简单。
- 导出流程清晰。
- 加载、空数据、错误和成功状态都有合理反馈。

页面可以使用中文作为第一版界面语言，但产品术语应尽量符合海外营销业务的实际用法。结构应方便未来增加英文界面。

不要仅为美观牺牲可解释性，也不要把所有信息挤在一个巨大表格里。可以用摘要卡片、筛选器、详情展开区和对比视图，但不要无意义地堆砌图表。

演示时必须能够在几分钟内完整呈现：
1. 选择一个营销任务。
2. 加载模拟达人数据。
3. 查看规则初筛。
4. 运行 AI 分析。
5. 打开一名达人的详细分析并核查证据。
6. 修改人工审核结果。
7. 导出结果。

如果 API 不可用，演示流程仍应清晰说明哪些环节可以运行、哪些环节需要配置 API。

## 八、测试与验收标准

每个核心功能都必须有明确的完成定义，不能以“代码已写完”作为验收标准。

### 必须覆盖的测试

1. 正常 CSV 导入。

优先使用自动化测试验证核心业务逻辑；界面层再通过实际运行检查关键用户流程。

## 十、分阶段执行计划
